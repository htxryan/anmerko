# Finish a feature

Code, tests, and a green PR are not the whole feature. A user learns about it
from the docs, the brochure, a clip, and the store listing; any of them left
stale is a bug. Run this after the implementation works and before the PR is
final. Work in the feature's worktree and ship everything in the same PR.

Skip a surface only when the feature truly does not touch it, and say so in the
PR. Internal refactors, CI, and test-only changes do not need this skill.

## 1. Sweep for claims the feature makes false

Before writing anything new, search for statements the change contradicts:
limits, formats, "only" / "never" / "cannot" wording, counts, and button lists.

```sh
git grep -n -i -E '<old behavior>|<limit>|<format>|never|only' -- site/src docs README.md src
```

Example: full-page screenshots made "Only the cropped PNG is stored — never a
full-page capture" false on the Features page, and JPEG fallback made "attach
the PNG files" incomplete in three docs. Fix every hit in the same PR.

## 2. User docs — `site/src/content/docs/docs/`

- Update the usage page for the flow (`usage/*.md`): steps, the exact button
  labels as rendered, limits, timing, and known limitations.
- New page: add it to the sidebar in `site/astro.config.mjs`.
- Check the cross-cutting pages every time: `usage.md` (feature summary list),
  `privacy.md` (what is stored or captured), `troubleshooting.md` (new failure
  or cancel paths), `send-to-your-agent.md` and `example-prompt.md` (prompt or
  export format), `settings.md` (new preferences).
- `example-prompt.md` is generated by `docs/store/capture.mjs`; edit the
  generator's text as well so a recapture does not revert the page.
- The in-site demo cannot use extension-only capabilities (screenshots,
  component context). State that where relevant rather than implying the demo
  supports it.

## 3. Brochure Features page — `site/src/pages/features.astro`

- Add or extend a `feature-split` section: text left (`h2` with an `id`, one
  lede paragraph, 2–3 concrete bullets, a docs link), clip right in a
  `feature-clip` figure. Keep the tone and length of the sibling sections.
- Update the page `<meta name="description">` if the feature is headline-level.
- Consider the homepage "Why anmerko" cards and hero copy in
  `site/src/pages/index.astro` only for headline features; do not churn them
  for small options.

## 4. Demo clip — follow [docs/feature-clips.md](../../../docs/feature-clips.md)

That guide is the source of truth for the locked look, the honesty
constraints, and the encode settings. The steps in brief:

1. Add a scenario to `scripts/site/capture-feature-clips.mjs` using the
   existing cadence (`setupPage` → `caption` → `glide` → `clickAt` →
   `pressSequentially` → closing hold), register it in `clips` and the default
   list, and add it to the usage line and the guide.
2. Keep the cursor overlay out of anything the extension captures: call
   `hideOverlay(page, true)` around every click or drag that triggers a
   screenshot, including the **Take Screenshot** click itself, whose viewport
   capture becomes the selection backdrop. Otherwise the recording shows a
   frozen second cursor.
3. Record: `npm run build`, then
   `HEADLESS=1 CLIP_VIEWPORT=1068x668 CLIP_SCALE=800:-2 FFMPEG=<ffmpeg> node scripts/site/capture-feature-clips.mjs <name>`.
   If Homebrew `ffmpeg` fails with missing dylibs, use a static build outside
   the repository, for example
   `npm install --prefix /tmp/anmerko-ffmpeg ffmpeg-static` and
   `FFMPEG=/tmp/anmerko-ffmpeg/node_modules/ffmpeg-static/ffmpeg`. It needs
   libx264 and libass (`ffmpeg -encoders | grep libx264`,
   `ffmpeg -filters | grep subtitles`).
4. Review the clip frame by frame before embedding it:
   `"$FFMPEG" -i site/public/media/features/<name>.mp4 -vf "fps=2,scale=400:-2,tile=4x4" /tmp/<name>-%d.png`,
   then look at the sheets. Check the captions, the single cursor, no
   extension UI inside captured images, and a readable final state. Budget
   about 10–20 s and roughly 100–150 KB.
5. Embed with the `?v=${CLIP_V}` URL and an existing poster from
   `site/public/screenshots/`. Bump `CLIP_V` only when the bytes of an
   existing clip change.

## 5. Store surfaces — `docs/store/`

- `listing-copy.md`: update the description and bullets when the feature
  changes what anmerko does. This is source copy only; never submit or
  publish store changes without explicit approval.
- `site/public/screenshots/` (shared by docs and stores, recaptured with
  `docs/store/capture.mjs` in installed Chrome): if the feature visibly
  changes UI shown in them, recapture and update `capture.json`. If you
  cannot, list the stale screenshot in the PR as follow-up work.

## 6. Verify

```sh
npm run site:build && npm run site:check && npm run site:test
```

Then serve `site/dist` locally, open the Features page and each changed docs
page in a browser, confirm the new section renders and the clip loads and
plays (`readyState` ≥ 2, `currentTime` advancing), and look at a screenshot
of it. Extension checks (`npm run check`, manual browser testing) remain
required by the normal workflow.

## 7. Report in the PR

Add a short "Public surfaces" list to the PR description: each surface
updated, each one deliberately left unchanged with the reason, and any
follow-up such as a store screenshot recapture. When you tell the user the
feature is done, include the same list.
